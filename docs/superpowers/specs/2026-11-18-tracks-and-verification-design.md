# 상담사 라이프사이클 확장 — 직군 트랙 + 보완 2건 설계 문서

작성일: 2026-11-18 · 상태: 승인됨 (2026-11-18)
대상 코드: `agent-lifecycle/` (기존 설계: `2026-11-18-agent-lifecycle-course-design.md`)

## 1. 의도와 이유

기존 강의(6단계, 한국어/영어)는 그대로 두고 두 가지를 더한다.

1. **보완 2건.** COPC CX Standard 7.0의 목차 제목과 비교했을 때 강의에 빠져 있던 주제 중 두 가지를 넣는다: 스킬·지식 검증, QA 캘리브레이션. COPC 본문은 쓰지 않고, 내용은 다른 공개 자료와 일반 실무 지식으로 쓴다.
2. **직군 트랙.** 같은 6단계를 유지하면서 화면에서 "일반 고객지원 / 기술지원"을 고르면 그 직군에만 해당하는 스텝과 문제가 추가로 나온다. 신입 팀장이 자기 팀 직군에 맞는 내용을 보되, 라이프사이클이라는 큰 흐름은 공통으로 유지하기 위해서다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 레슨 2에 스킬 검증, 레슨 4에 캘리브레이션을 추가한다.
- 6개 레슨 모두에 트랙별 내용이 있다 (트랙을 바꾸면 어느 레슨에서든 차이가 보인다).
- 트랙 선택은 언어 선택처럼 기억된다.
- 한국어 먼저 → 사용자 확정 → 영어 번역 (기존과 같은 순서).

**비목표**
- 채팅·이메일 등 채널별 구분, 세 번째 직군.
- 목차 비교에서 나온 나머지 주제(직무 정의, 결근, 직원 피드백, 스케줄 준수, 지식 관리, 컴플라이언스) — 이번에는 넣지 않는다.
- 저장소의 다른 Knowledge Base 주제.

**반목표**
- COPC 문서의 문장·요건·배점을 옮기거나, 강의가 COPC 인증 자료처럼 보이는 것.
- 기존 설계의 반목표 전부 (출처 없는 수치, "진상" 표현, 빽빽한 글).
- 한 직군이 다른 직군보다 낫다는 인상을 주는 서술.

## 3. 결정된 사항

### 3.1 사용자 결정
- 트랙 방식: **같은 6단계에 트랙 전환** (별도 강의 2개, 공통+심화 레슨 방식은 선택하지 않음).
- 보완은 추천안 2건(스킬 검증, 캘리브레이션)만 반영.
- COPC는 목차 제목만 참고.

### 3.2 화면 동작 (제작자 제안)
- 상단에 언어 버튼 옆으로 트랙 버튼 `일반 고객지원 | 기술지원` (영어: `General support | Tech support`).
- 처음 방문 시 기본값은 일반 고객지원. 홈 화면에 트랙을 고르는 안내 한 줄을 둔다.
- 레슨의 스텝은 "공통 스텝 + 현재 트랙 스텝"을 순서대로 보여 준다. 트랙 전용 스텝에는 직군 표시(작은 라벨)를 붙여 공통 내용과 구분한다.
- 레슨 도중 트랙을 바꾸면 방금 보던 스텝에서 가장 가까운 앞쪽 공통 스텝으로 이동한다. 체크포인트 화면에서 바꾸면 체크포인트를 새 트랙 기준으로 다시 보여 준다(답은 초기화).
- 주소 형식(`#hiring-3`)은 그대로다. 숫자는 "현재 트랙에서 보이는 스텝 순서"를 뜻한다. 링크를 받은 사람은 자기 트랙 기준으로 열린다.
- 완료 표시는 지금처럼 레슨 단위다 (어느 트랙으로 마쳐도 완료).

### 3.3 데이터 구조 (제작자 제안)
- 스텝과 체크포인트 문항에 선택 필드 `track: 'general' | 'tech'`를 둔다. 없으면 공통이다.
- 다이어그램 노드·엣지는 지금처럼 스텝의 `show`로 제어하므로 트랙 전용 노드도 같은 방식으로 추가한다.
- 점검 규칙 변경:
  - 트랙별로 보이는 스텝 수는 6–12개 (기존 6–10에서 상향. 보완·트랙 스텝이 들어갈 자리).
  - 모든 레슨에 트랙마다 전용 스텝이 1개 이상.
  - 트랙별로 보이는 체크포인트 문항은 1–2개. (2026-11-20 변경: 2–3개. 공통 1 + 직군 2. `2026-11-20-lifecycle-track-questions.md`)
  - 나머지 규칙(문장 수, 금지어, 수치 표시, 지민 등장, 영어 규칙)은 그대로.

### 3.4 보완 내용 (제작자 초안 — 사용자 문안 검토 대상)
- **레슨 2 온보딩 — 스킬 검증 (공통, 2스텝 + 노드 "스킬 검증").** 교육을 마친 것과 실전에 준비된 것은 다르다. 교육 끝에 모의 콜 평가와 지식 시험으로 합격 기준을 확인하고, 통과해야 네스팅으로 간다. 미달이면 탈락이 아니라 보충 교육 후 재평가한다. 합격 기준은 센터마다 다르다.
- **레슨 4 성과·코칭 — 캘리브레이션 (공통, 1스텝 + 노드 "캘리브레이션").** 팀장과 QA 담당이 같은 콜을 각자 채점한 뒤 모여 기준을 맞춘다. 평가자마다 점수가 다르면 코칭의 근거가 흔들린다. 주기는 센터마다 다르다.
- 레슨 4에는 한 줄로 재검증도 언급한다: 상품·정책이 바뀌면 지식을 다시 확인한다.

### 3.5 트랙별 내용 (제작자 초안 — 사용자 문안 검토 대상)

| 단계 | 일반 고객지원 | 기술지원 |
|---|---|---|
| 1 채용 | 폭넓은 문의를 다루는 대화력·공감, 정책 안에서 해결책을 찾는 유연성 | 단계적으로 원인을 좁혀 가는 문제 해결력, 기술 내용을 쉬운 말로 설명하는 능력. 모의 상담에 장애 진단 상황 |
| 2 온보딩 | 넓은 범위의 상품·정책·절차, 문의 유형별 응대 흐름 | 제품 구조, 진단 도구, 티켓 기록 방법, 지식 자료 찾는 법. 제품이 바뀔 때마다 교육이 이어진다 |
| 3 네스팅 | 쉬운 문의 유형부터 차례로 맡긴다 | 1차 지원 범위의 쉬운 이슈부터. 상위 단계로 넘기는(에스컬레이션) 기준을 익힌다: 시간, 난이도, 고객 영향 |
| 4 성과·코칭 | CSAT와 FCR 중심. QA는 공감·안내 정확도 | 해결 시간, 에스컬레이션 비율, 티켓 기록 품질. QA는 진단 과정이 맞았는지 |
| 5 유지 | 반복 업무와 감정노동의 누적 | 어려운 문제의 인지 부담, 학습 시간 보장, 기술 성장 기회 |
| 6 경력 | QA, 교육 강사, 팀 리더, WFM | 위 경로에 더해 2차·3차 지원, 지식 자료 담당, 제품·개발 조직과의 연계 |

- 지민의 이야기(결말: QA 담당)는 두 트랙 공통이다. 트랙 스텝에서는 지민이 그 직군 상황을 겪는 장면으로 쓴다.
- 수치는 넣지 않는다. 기관·센터에 따라 달라지는 것은 "센터마다 다름"으로 쓴다.

### 3.6 만드는 방법 (제작자 선택)
- 기존 구조 유지: 정적 파일, `agent-lifecycle/js/lessons/*.js` 데이터 + 공통 엔진·렌더러.
- 트랙 선택·저장은 언어 선택과 같은 방식의 모듈로 둔다.
- 순서: 엔진(트랙 필터·저장·점검 규칙) → 화면(트랙 버튼·라벨) → 한국어 내용 → 사용자 문안 확정 → 영어.
- 작업은 `main`에 합쳐진 뒤의 코드를 기준으로 별도 브랜치에서 하고 Pull Request로 올린다.

### 3.7 검토 후 제작자 판단 (사용자 확인 가능)
- **기존 문안 수정 허용 범위.** 새 내용과 어긋나는 곳만 고친다. 레슨 2의 마지막 스텝과 다음 단계 연결 문구는 "교육 → 스킬 검증 통과 → 네스팅" 흐름에 맞게 고친다. 그 밖의 확정된 문안은 건드리지 않는다. 고친 문장은 한국어·영어 모두 사용자 검토 목록에 올린다.
- **공통 스텝은 공통으로 둔다.** AHT·FCR·CSAT, QA·강사·팀 리더·WFM 경로처럼 두 직군에 모두 해당하는 기존 스텝은 그대로 공통이다. 일반 고객지원 전용 스텝은 3.5 표의 내용 중 공통 스텝에 없는 것만 쓴다. 레슨 4는 "문의 유형이 다양해 QA에서 정책 안내의 정확도와 공감 표현을 본다", 레슨 6은 "전문 상담(예: 해지 상담, VIP 상담) 담당으로 넓히는 길"로 한다.
- **트랙 전용 문제.** 레슨마다 트랙별 전용 문제를 1개씩 둔다. 각 트랙에서 공통 1문제 + 전용 1문제가 보인다 (새 문제 12개).
- **공개 순서.** 한국어 내용은 비공개 아티팩트 미리보기로 검토받는다. GitHub `main`에는 영어 번역까지 끝난 뒤 한 번에 합친다. 그동안 공개 사이트는 지금 버전 그대로다.
- **스텝 수.** 레슨 4는 공통 10 + 트랙 1–2로 상한(12)에 닿는다. 상한을 넘기면 기존 스텝을 합치지 않고 트랙 스텝을 줄인다.

### 3.8 기술지원 트랙의 응대 방식 (사용자 답변, 2026-11-18)
- 기술지원 팀은 **전화·채팅·이메일 모든 채널의 티켓을 지원하는 조직**이다.
- 그래서 (제작자 판단) 통화를 다루는 기존 공통 스텝은 기술지원에도 해당하므로 공통으로 둔다. 기술지원 전용 스텝은 "티켓" 단위로 쓴다: 어느 채널로 들어오든 티켓으로 기록되고, 해결·인계·종결된다. 글로 응대하는 능력(채팅·이메일)을 채용과 교육에서 언급한다.
- 채널별로 내용을 따로 나누는 것은 여전히 비목표다.

### 3.9 PR 검토 후 사용자 결정 (2026-11-18)
- 채널별 기록의 이름: 전화는 녹취(Call Recording), 채팅은 채팅 로그(Chat Log), 이메일은 이메일 로그(Email Log).
- 처음 접속하면 "일반 고객지원" + "한국어"로 연다 (브라우저 언어를 따르지 않는다).
- 직군 라벨은 화면 낭독기가 읽지 않아도 된다. 내용 점검기에 문제 ID 중복·마지막 스텝 공통 여부 검사는 넣지 않는다.
- 레슨 4 다이어그램은 화살표 길이가 비슷하도록 상자 간격을 다시 잡는다. 좁은 화면의 상단 버튼은 두 줄 이내로 줄인다.

## 4. 검토한 접근법

| 접근 | 장점 | 단점 | 결과 |
|---|---|---|---|
| **A. 같은 6단계에 트랙 전환** | 큰 흐름 유지, 차이가 단계별로 나란히 보임, 공통 문안 한 벌 | 데이터 구조·점검 규칙·주소 의미 변경 | **선택 (사용자)** |
| B. 직군별 별도 강의 2개 | 직군별로 깊이 있게 | 공통 부분 중복, 문안 두 배 | 선택 안 함 |
| C. 공통 강의 + 직군별 심화 레슨 | 가장 빠름 | 단계별 차이가 한눈에 안 보임 | 선택 안 함 |

## 5. 제작자에게 맡기는 것
- 트랙 버튼과 직군 라벨의 모양, 트랙 전용 노드의 배치.
- 스텝별 캡션과 문제 문안 (3.4·3.5 범위 안에서, 사용자 검토 전제).
- 파일 구성, 테스트 구성.
