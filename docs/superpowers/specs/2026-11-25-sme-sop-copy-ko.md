# 직무전문가 SOP 라이브러리 — 한국어 문안 초안

작성일: 2026-11-25 · 상태: 승인됨 (2026-11-25) · 설계: `2026-11-25-sme-learn-set-design.md` §4.3

공통 원칙: 스텝은 3문장 이내로 씁니다. 출처 없는 숫자에는 "예시"를 붙입니다. 시점은 "당신 = 직무전문가"입니다.

다른 강의와 겹치지 않게 하는 방법:
- 직무전문가 첫걸음은 직무전문가가 된 직후의 적응을, 직무전문가 서포트 라이프사이클은 상담사가 자라는 단계별 지원을 다룹니다. 이 강의는 **절차 하나하나를 순서대로** 다룹니다. 단계 이름, 누가 하는지, 무엇을 기록하고 어디로 보내는지가 중심입니다.
- 팀장 SOP와 같은 절차(에스컬레이션, 스크러빙, 캘리브레이션)는 직무전문가가 맡는 부분만 다루고, 팀장 SOP를 가리킵니다. 스크러빙의 L1·L2 분류는 팀장 SOP와 같은 기준입니다(L1: 원인이 있는 곳, L2: BPO가 통제할 수 있는지).
- 확인 문제는 앞의 두 강의와 같은 장면을 피하고, 절차의 세부(기록, 분류, 전달 경로)를 묻습니다.

## 레슨 1. 에스컬레이션 승인

| 항목 | 한국어 |
|---|---|
| 제목 | 에스컬레이션 승인 |
| 짧은 이름 | 승인 |
| 부제 | 넘어온 건을 확인하고, 범위 안이면 승인하고, 밖이면 넘깁니다. |
| 누가 | 상담사 → 직무전문가 → 팀장 |
| 노드 | 요청 확인 · 범위 판단 · 승인 또는 처리 · 팀장 인계 · 기록 남기기 |

스텝:

1. 이 절차의 목적은 상담사가 요청한 에스컬레이션을 같은 기준으로 빠르게 판단해, 승인하거나 직접 처리하거나 팀장에게 넘기는 것입니다. 팀장 SOP의 고객 불만 에스컬레이션에서 직무전문가가 넘겨받은 다음 부분입니다.
2. 지민이 메신저로 보상 승인을 요청합니다. 첫 단계는 요청 확인입니다. 티켓에 고객 요청, 지민이 이미 해 본 것, 고객 상태가 적혀 있는지 봅니다.
3. 기록이 부족하면 지민에게 짧게 되묻습니다. 고객에게 같은 질문을 다시 하지 않기 위해서입니다.
4. 둘째 단계는 범위 판단입니다. 팀장과 맞춰 둔 승인 범위 목록을 기준으로, 내 범위 안인지 밖인지 정합니다. 확실하지 않으면 범위 밖으로 봅니다.
5. 셋째 단계는 승인 또는 처리입니다. 범위 안이면 승인하고, 상담사가 풀기 어려운 건은 직무전문가가 이어받아 직접 응대합니다. 이어받을 때는 고객에게 이전 내용을 알고 있다고 먼저 말합니다.
6. 넷째 단계는 팀장 인계입니다. 범위 밖이거나 정책에 없는 요청은 팀장에게 넘깁니다. 그동안 고객에게 기다림을 안내하도록 지민에게 부탁합니다.
7. 다섯째 단계는 기록 남기기입니다. 승인했든 넘겼든 티켓에 결정과 이유를 적고, 승인 기록에도 남깁니다. 같은 요청이 다시 오면 누구든 같은 기준으로 판단할 수 있습니다.
8. 답하는 데 시간이 걸리면 언제 답할지 먼저 알립니다(예시: 5분 안에). 상담사가 기다리는 동안 고객도 기다리고 있습니다.

체크포인트:

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 지민의 보상 요청이 범위 안이라 승인했습니다. 다음으로 할 일은 무엇일까요? |
| 보기 a (오답) | 승인했으니 따로 남길 것은 없다. |
| a 피드백 | 이유가 남지 않으면 비슷한 요청이 왔을 때 사람마다 다르게 판단하게 됩니다. |
| 보기 b (정답) | 티켓과 승인 기록에 결정과 이유를 적는다. |
| 보기 c (오답) | 승인해도 되는지 팀장에게 다시 묻는다. |
| c 피드백 | 범위 안의 건까지 다시 물으면 팀장의 하루가 막히고, 승인 범위를 맞춘 의미가 없어집니다. |
| 해설 | 승인은 결정과 이유를 기록해야 끝납니다. 그래야 같은 기준이 이어집니다. |
| 2번 질문 | 지민이 풀기 어려운 건을 직무전문가가 이어받아 고객과 통화합니다. 먼저 할 말로 알맞은 것은 무엇일까요? |
| 보기 a (오답) | "처음부터 다시 설명해 주시겠어요?" |
| a 피드백 | 고객은 같은 이야기를 되풀이하는 것을 가장 싫어합니다. 기록을 읽고 이어받습니다. |
| 보기 b (정답) | "앞서 상담하신 내용을 확인했습니다. 이어서 도와드리겠습니다." |
| 보기 c (오답) | "앞 상담사가 실수한 것 같습니다." |
| c 피드백 | 동료를 탓하면 고객의 신뢰가 떨어지고, 문제는 그대로 남습니다. |
| 해설 | 이어받을 때는 이전 내용을 알고 있다고 먼저 말합니다. |
| 다음 레슨 연결 | 에스컬레이션은 지금 들어온 문제를 푸는 일입니다. 다음은 이미 끝난 티켓에서 문제를 찾는 스크러빙입니다. |

## 레슨 2. 스크러빙

| 항목 | 한국어 |
|---|---|
| 제목 | 스크러빙 |
| 짧은 이름 | 스크러빙 |
| 부제 | 매일 몇 건씩 다시 읽고, 원인을 찾아 분류해 보냅니다. |
| 누가 | 직무전문가 → 팀장 · 고객사 |
| 노드 | 대상 고르기 · 원인 분석 · L1·L2 분류 · 기록과 전달 |

스텝:

1. 이 절차의 목적은 처리된 티켓과 쌓인 티켓을 다시 읽어 진짜 원인을 찾고, 고칠 수 있는 곳으로 보내는 것입니다. 팀장 SOP의 스크러빙 가운데 직무전문가가 매일 맡는 부분입니다.
2. 첫 단계는 대상 고르기입니다. DSAT, CSAT, 미해결 순서로 티켓을 고릅니다. 매일 3~4건(예시)씩 꾸준히 봅니다.
3. 둘째 단계는 원인 분석입니다. 고객이 처음 원한 것, 상담사가 한 것, 결과가 어긋난 지점을 찾아 한두 문장으로 요약합니다.
4. 원인은 "왜"를 몇 번 물어 끝까지 갑니다. "안내가 틀렸다"에서 멈추지 않고, 왜 틀렸는지, 문서가 없었는지, 문서가 오래됐는지까지 봅니다.
5. 셋째 단계는 L1·L2 분류입니다. L1은 원인이 있는 곳(제품, 절차, 지원, 고객, 기타)으로, L2는 BPO가 통제할 수 있는 원인인지로 나눕니다. 팀장 SOP의 스크러빙과 같은 기준입니다.
6. 넷째 단계는 기록과 전달입니다. 결과를 스크러빙 시트에 티켓 번호와 함께 적습니다. 상담사의 행동에서 나온 원인은 팀장에게 건네는 트렌드 요약으로, 통제할 수 없는 원인은 VOC 리포트로 이어집니다.
7. 서준의 티켓에서 확인 단계 누락을 찾았다면, 한 번은 서준에게 짧게 알려 주고, 반복되면 요약에 담습니다. 팀 채팅방에 이름을 밝혀 올리지 않습니다.

체크포인트:

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 오늘 스크러빙할 티켓을 고르는 순서로 알맞은 것은 무엇일까요? |
| 보기 a (오답) | 처리 시간이 가장 짧았던 티켓부터 |
| a 피드백 | 처리 시간으로는 고객이 만족했는지 알 수 없습니다. 고객이 만족하지 못한 티켓에서 원인이 먼저 보입니다. |
| 보기 b (정답) | DSAT, CSAT, 미해결 순서로 |
| 보기 c (오답) | 잘 아는 상담사의 티켓부터 |
| c 피드백 | 사람을 골라 보면 원인이 아니라 사람을 보게 되고, 공정하지도 않습니다. |
| 해설 | 고객이 만족하지 못한 티켓부터 봐야 고칠 원인이 먼저 나옵니다. |
| 2번 질문 | 환불이 늦어 DSAT가 난 티켓을 보니 상담사 안내는 맞았고, 원인은 고객사 결제 시스템 장애였습니다. 어떻게 분류하고 어디로 보낼까요? |
| 보기 a (오답) | 고객이 화가 났으니 상담사 응대 문제로 보고 트렌드 요약에 담는다. |
| a 피드백 | 상담사는 안내를 제대로 했습니다. 상담사의 행동이 아닌 원인을 코칭으로 보내면 고쳐지지 않습니다. |
| 보기 b (정답) | BPO가 통제할 수 없는 원인으로 분류하고, VOC 리포트로 고객사에 전한다. |
| 보기 c (오답) | 분류하기 애매하니 기록하지 않는다. |
| c 피드백 | 기록하지 않으면 같은 불만이 쌓여도 고객사에 전할 근거가 남지 않습니다. |
| 해설 | L2는 BPO가 통제할 수 있는지로 나눕니다. 통제할 수 있으면 우리가 바꾸고, 없으면 고객사에 요청합니다. |
| 다음 레슨 연결 | 스크러빙에서 찾은 상담사의 행동은 팀장에게 갑니다. 다음은 그 요약을 만드는 절차입니다. |

## 레슨 3. 상담 트렌드 요약 보고

| 항목 | 한국어 |
|---|---|
| 제목 | 상담 트렌드 요약 보고 |
| 짧은 이름 | 트렌드 요약 |
| 부제 | 스크러빙에서 본 것을 팀장이 코칭에 바로 쓸 수 있게 정리합니다. |
| 누가 | 직무전문가 → 팀장 |
| 노드 | 모으기 · 반복 찾기 · 한 줄로 쓰기 · 보고하기 |

스텝:

1. 이 절차의 목적은 스크러빙에서 본 상담사별 반복 행동을 정리해, 팀장이 누구를 무엇으로 코칭할지 바로 정하게 돕는 것입니다.
2. 수진 팀장은 매주 금요일(예시) 이 요약을 받아 다음 주 코칭 계획을 세웁니다.
3. 첫 단계는 모으기입니다. 한 주 동안 스크러빙 시트에 적은 원인 가운데 상담사의 행동에서 나온 것을 상담사별로 모읍니다.
4. 둘째 단계는 반복 찾기입니다. 같은 행동이 두 번 이상(예시) 나온 것만 트렌드로 봅니다. 한 번은 실수이고, 반복은 코칭할 행동입니다.
5. 셋째 단계는 한 줄로 쓰기입니다. 사람, 행동, 횟수, 티켓 번호를 적습니다. 예를 들어 "지민: 환불 문의 3건(예시)에서 본인 확인 다음 단계 누락"처럼 씁니다.
6. 성격이나 태도가 아니라 행동을 씁니다. 점수를 매기거나 순위를 만들지 않고, 코칭으로 바꿀 수 있는 것만 담습니다.
7. 넷째 단계는 보고하기입니다. 정해진 날 수진 팀장에게 보냅니다. 여러 사람에게 같은 행동이 나왔다면 따로 묶어 허들 주제로 제안합니다.
8. 준호처럼 다른 상담사를 잘 돕는 모습이 반복되면 그것도 적습니다. 요약은 고칠 점만이 아니라 팀장이 칭찬하고 키울 사람도 알려 줍니다.

체크포인트:

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 이번 주 서준의 티켓 한 건에서 확인 단계 누락을 봤습니다. 요약에 어떻게 담을까요? |
| 보기 a (오답) | 서준의 트렌드로 적는다. |
| a 피드백 | 한 번은 아직 트렌드가 아닙니다. 다음 주에도 나오는지 봅니다. |
| 보기 b (정답) | 서준에게 짧게 알려 주고, 반복될 때 요약에 담는다. |
| 보기 c (오답) | 팀 전체 문제로 허들에 올린다. |
| c 피드백 | 한 사람의 한 번 실수를 팀 전체 문제로 올리면, 다른 상담사에게는 필요 없는 이야기가 됩니다. |
| 해설 | 반복된 행동만 트렌드로 요약합니다. |
| 2번 질문 | 이번 주 팀원 다섯 명에게서 같은 안내 실수가 나왔습니다. 어떻게 할까요? |
| 보기 a (오답) | 다섯 명을 각각 한 줄씩만 적는다. |
| a 피드백 | 각각만 적으면 팀 공통 문제라는 것이 보이지 않습니다. |
| 보기 b (정답) | 팀 공통 트렌드로 묶어 허들 주제로 제안하고, 원인이 문서라면 지식 베이스 업데이트도 요청한다. |
| 보기 c (오답) | 다섯 명에게 각각 주의를 준다. |
| c 피드백 | 공식 주의나 경고는 팀장의 몫입니다. 여러 명이 같다면 원인이 사람보다 문서나 교육에 있을 수 있습니다. |
| 해설 | 여러 사람에게 같은 실수가 나오면 사람보다 원인을 먼저 봅니다. |
| 다음 레슨 연결 | 팀장을 돕는 일은 요약만이 아닙니다. 팀장이 자리에 없을 때는 출석도 대신 확인합니다. |

## 레슨 4. 출석 관리 대행

| 항목 | 한국어 |
|---|---|
| 제목 | 출석 관리 대행 |
| 짧은 이름 | 출석 대행 |
| 부제 | 기록하고 알리는 데까지, 판단과 조치는 팀장이 합니다. |
| 누가 | 직무전문가 → 팀장 · RTA |
| 노드 | 대행 확인 · 출석 확인 · 사실 기록 · 공백 알리기 |

스텝:

1. 이 절차의 목적은 팀장이 자리에 없거나 팀원이 많을 때, 직무전문가가 출석을 대신 확인하고 기록해 인원 공백을 빨리 알리는 것입니다.
2. 첫 단계는 대행 확인입니다. 수진 팀장에게 오늘 대행을 맡는지, 연락 올 곳과 보고할 시각을 미리 받습니다.
3. 둘째 단계는 출석 확인입니다. 근무 시작 시각에 스케줄과 실제 로그인을 맞춰 보고, 없는 사람을 확인합니다.
4. 지각이나 결근 연락이 오면 받은 시각과 말한 사유를 그대로 받습니다. 사유가 타당한지는 판단하지 않고, 건강 같은 개인 사정은 캐묻거나 자세히 적지 않습니다.
5. 셋째 단계는 사실 기록입니다. 출석 시트에 도착 시각, 연락 여부, 사유를 사실대로 적습니다. 빼거나 고치지 않습니다.
6. 넷째 단계는 공백 알리기입니다. 결근으로 인원이 부족하면 RTA와 수진 팀장에게 바로 알려 대기열을 지킬 수 있게 합니다.
7. 정해진 시각에 수진 팀장에게 출석 결과를 보냅니다. 경고, 근태 조치, 스케줄 변경은 팀장이 정합니다.

## 레슨 5. 고객사 업데이트 허들

| 항목 | 한국어 |
|---|---|
| 제목 | 고객사 업데이트 허들 |
| 짧은 이름 | 업데이트 허들 |
| 부제 | 바뀐 정책을 먼저 이해하고, 상담사가 고객에게 할 말까지 준비합니다. |
| 누가 | 고객사 → 직무전문가 → 상담사 전체 |
| 노드 | 내용 이해 · 안내 준비 · 허들 진행 · 후속 공유 |

스텝:

1. 이 절차의 목적은 고객사가 보낸 정책이나 프로모션 업데이트를 팀 전체가 같은 날, 같은 내용으로 고객에게 안내하게 하는 것입니다.
2. 오후에 고객사가 환불 기간 변경 공지를 보내왔습니다. 내일부터 적용됩니다.
3. 첫 단계는 내용 이해입니다. 무엇이 언제부터 바뀌는지, 누구에게 적용되는지 확인합니다. 모호한 부분은 허들 전에 수진 팀장이나, 정해진 경로로 고객사 담당에게 묻습니다.
4. 둘째 단계는 안내 준비입니다. 바뀐 점을 세 줄 이내로 정리하고, 상담사가 고객에게 할 안내 문장과 예상 질문의 답을 만듭니다.
5. 셋째 단계는 허들 진행입니다. 교대 시작 전 짧은 허들(예시: 5분)에서 바뀐 점, 안내 문장, 적용 시각을 전합니다. 근무 시간이 다른 상담사를 위해 같은 내용을 글로도 남깁니다.
6. 허들에서 바로 답하지 못한 질문은 적어 두고, 확인한 뒤 답합니다. 추측으로 답하면 팀 전체가 잘못 안내하게 됩니다.
7. 넷째 단계는 후속 공유입니다. 허들에서 나온 질문과 답을 팀 채팅방에 올리고, 지식 베이스에 반영되도록 요청합니다.
8. 적용 첫날에는 스크러빙에서 바뀐 정책과 관련된 티켓을 먼저 봅니다. 잘못 안내된 건이 있으면 바로 다시 알립니다.

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 공지의 "일부 회원"이 누구인지 분명하지 않은데, 허들은 10분 뒤입니다. 어떻게 할까요? |

| 해설 | 허들에 오지 못한 사람에게도 같은 날, 같은 내용이 닿아야 합니다. |
| 다음 레슨 연결 | 직무전문가가 팀에 전하는 기준은 고객사 공지만이 아닙니다. 품질 평가 기준도 직무전문가가 현장에 전합니다. |

## 레슨 6. 캘리브레이션 참여와 기준 전달

| 항목 | 한국어 |
|---|---|
| 제목 | 캘리브레이션 참여와 기준 전달 |
| 짧은 이름 | 캘리브레이션 |
| 부제 | 현장의 사정을 세션에 가져가고, 맞춘 기준을 현장에 가져옵니다. |
| 누가 | QA · 직무전문가 · 팀장 → 상담사 |
| 노드 | 사례 보내기 · 독립 평가 · 현장 사정 전하기 · 기준 전달 |

스텝:

1. 이 절차의 목적은 캘리브레이션에서 직무전문가가 현장 사정을 알려 평가 기준을 현실에 맞추고, 바뀐 기준을 상담사에게 먼저 전하는 것입니다. 세션 진행은 팀장 SOP의 캘리브레이션을 따릅니다.
2. 첫 단계는 사례 보내기입니다. 지민이 현장 방식대로 처리했는데 감점된 티켓처럼, 평가 기준과 현장 방식이 엇갈린 사례를 골라 세션 전에 QA에게 보냅니다.
3. 둘째 단계는 독립 평가입니다. 다른 사람의 점수를 보기 전에, 기준표에 따라 직접 점수를 매기고 이유를 적습니다.
4. 셋째 단계는 현장 사정 전하기입니다. 점수가 갈린 항목에서, 상담사가 그 순간 화면에서 무엇을 볼 수 있었고 어떤 도구를 썼는지 설명합니다.
5. 직무전문가는 상담사 편을 드는 자리가 아닙니다. 현장 사정을 알려 기준이 현실에 맞게 정해지도록 돕는 자리입니다.
6. 넷째 단계는 기준 전달입니다. 합의로 기준이 바뀌면, 그 기준으로 평가받기 전에 상담사들이 알도록 팀장과 맞춰 허들과 팀 채팅방에서 먼저 전합니다. QA의 공식 공유가 나오면 그 내용도 다시 알립니다.
7. 바뀐 기준은 예시 한 건과 함께 전합니다. "이제 이렇게 하면 됩니다"를 보여 주면 상담사가 바로 따라 할 수 있습니다.

## 레슨 7. VOC 리포팅

| 항목 | 한국어 |
|---|---|
| 제목 | VOC 리포팅 |
| 짧은 이름 | VOC |
| 부제 | 상담사 선에서 풀 수 없는 고객의 목소리를, 고객사가 쓸 수 있게 정리합니다. |
| 누가 | 직무전문가 → 팀장 → 고객사 |
| 노드 | 모으기 · 묶고 세기 · 리포트 쓰기 · 전달과 추적 |

스텝:

1. 이 절차의 목적은 고객이 반복해서 말하는 불만과 요청, 제품 의견을 모아, 고객사가 정책이나 제품을 고칠 근거로 전하는 것입니다.
2. 첫 단계는 모으기입니다. 스크러빙에서 통제할 수 없다고 분류한 원인, 에스컬레이션, 상담사들이 전한 고객의 말을 한곳에 모읍니다.
3. 둘째 단계는 묶고 세기입니다. 같은 주제끼리 묶고, 기간 동안 몇 건이었는지 셉니다. 고객의 실제 표현 한두 개를 그대로 붙여 둡니다.
4. 셋째 단계는 리포트 쓰기입니다. 주제마다 건수, 고객이 겪는 영향, 대표 사례, 제안을 적습니다.
5. 예를 들어 "배송 지연 안내 문자 없음: 주 40건(예시), 재문의로 이어짐, 출고 지연 시 문자 발송 제안"처럼 씁니다. 지민이 전한 고객의 말이 대표 사례가 될 수 있습니다.
6. 리포트에는 고객의 개인 정보와 상담사 이름을 넣지 않습니다. 고객사가 볼 것은 사람이 아니라 문제입니다.
7. 넷째 단계는 전달과 추적입니다. 리포트는 수진 팀장을 거쳐 고객사에 갑니다. 전달한 주제는 목록에 남기고, 바뀌었는지 다음 리포트에서 확인합니다.
8. 고객사가 고친 것이 생기면 팀에도 알립니다. 상담사는 자기가 들은 고객의 말이 무언가를 바꿨다는 것을 알 때 고객의 목소리를 더 잘 모읍니다.

체크포인트:

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 이번 주 "비밀번호 재설정 메일이 안 온다"는 문의가 많았습니다. 리포트 항목으로 알맞은 것은 무엇일까요? |
| 보기 a (오답) | "고객들이 비밀번호 때문에 화가 많이 남" |

## 레슨 8. 지식 베이스 업데이트 요청

| 항목 | 한국어 |
|---|---|
| 제목 | 지식 베이스 업데이트 요청 |
| 짧은 이름 | 지식 베이스 |
| 부제 | 틀리거나 빠진 문서를 찾으면, 고칠 사람이 바로 고칠 수 있게 요청합니다. |
| 누가 | 직무전문가 → 지식 베이스 담당 |
| 노드 | 문제 찾기 · 원문 확인 · 요청 쓰기 · 반영 확인 |

스텝:

1. 이 절차의 목적은 지식 베이스의 틀리거나 빠진 내용을 찾아 담당자가 바로 고칠 수 있게 요청하고, 고쳐지면 팀에 알리는 것입니다.
2. 첫 단계는 문제 찾기입니다. 서준과 지민이 같은 질문을 하거나, 스크러빙에서 문서대로 안내했는데 틀린 건이 나오면 문서를 의심합니다.
3. 둘째 단계는 원문 확인입니다. 정책 원문이나 고객사의 최신 공지와 문서를 비교해, 정말 틀렸는지 또는 빠졌는지 확인합니다.
4. 셋째 단계는 요청 쓰기입니다. 문서 이름, 틀린 문장, 바른 내용, 근거가 된 공지나 티켓 번호를 적어 정해진 경로로 보냅니다.
5. "환불 문서가 이상해요"처럼 보내면 담당자가 다시 물어야 합니다. 무엇을 무엇으로 바꿀지까지 적어야 빨리 고쳐집니다.
6. 고쳐지기 전까지는 팀 채팅방에 임시 안내를 올립니다. 문서를 고치는 동안에도 고객은 계속 문의합니다.
7. 넷째 단계는 반영 확인입니다. 문서가 고쳐지면 내용을 다시 확인하고, 허들이나 팀 채팅방에 바뀐 곳을 알립니다.

체크포인트:

| 항목 | 한국어 |
|---|---|
| 1번 질문 | 지식 베이스 업데이트 요청으로 알맞은 것은 무엇일까요? |
| 보기 a (오답) | "환불 문서 내용이 이상합니다." |
| a 피드백 | 무엇이 틀렸는지 담당자가 다시 찾아야 해서 반영이 늦어집니다. |
| 보기 b (정답) | "환불 문서 3번 항목의 신청 기간을 14일에서 7일로: 고객사 공지와 관련 티켓 2건 첨부" |
| 보기 c (오답) | 편집 권한이 있으니 검토 없이 바로 고친다. |
| c 피드백 | 검토 없이 고친 문서는 팀 전체의 안내를 한 번에 바꿉니다. 정해진 경로로 요청합니다. |
| 해설 | 요청에는 문서, 틀린 곳, 바른 내용, 근거를 적습니다. |
| 2번 질문 | 요청을 보냈지만 문서가 아직 고쳐지지 않았습니다. 그사이 할 일은 무엇일까요? |
| 보기 a (오답) | 고쳐질 때까지 기다린다. |
| a 피드백 | 그동안 상담사들은 틀린 문서대로 안내합니다. |
| 보기 b (정답) | 팀 채팅방에 임시 안내를 올리고, 반영되면 다시 알린다. |
| 보기 c (오답) | 상담사들에게 지식 베이스를 보지 말라고 한다. |
| c 피드백 | 지식 베이스 전체를 막으면 맞는 내용까지 찾을 곳이 사라집니다. |
| 해설 | 고쳐지기 전까지는 임시 안내로 빈틈을 막고, 반영되면 알립니다. |
| 마지막 연결 | 직무전문가 SOP 라이브러리를 마쳤습니다. 단계마다 어떤 절차를 쓰는지는 직무전문가 서포트 라이프사이클에서 다시 볼 수 있습니다. |
